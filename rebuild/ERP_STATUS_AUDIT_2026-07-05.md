# Axle ERP — Full Status Audit (2026-07-05)

**Method:** 16 parallel subsystem auditors reading real code -> adversarial re-verification of every critical/high risk against the cited source -> cross-cutting lead-reviewer synthesis. 25 agents, ~3.7M tokens, 781 tool calls.
**Note:** the dedicated Customers/CRM screens auditor failed to return (structured-output cap); customer findings below come from cross-cutting and adjacent audits and are marked partially verified.

## Overall grade: B-

The money/inventory core — the part that matters most — is genuinely sound: the PO -> receive -> moving-average-cost -> 3-way-match -> bill -> pay chain is the strongest subsystem in the app (A-, 169 passing tests), invoice totals run through one shared engine so List/workspace/print/CSV can never disagree, finalize/void are atomic against double-submit, payments correctly exclude reversed allocations everywhere, and the core-charge lifecycle (the most diesel-specific money path) is battle-tested end to end with real double-credit guards. A 10-step full-chain E2E test asserts every dollar to the cent. That is B+/A- work. What drags the program to B- is the layer AROUND the core: a confirmed-high counter-hot-path trust bug (quote header Disc% saves, flashes green 'Saved', and does absolutely nothing to the total), one real confirmed double-booking accounting bug (SO deposit 'convert to credit' leaves the money spendable twice, with a live UI form that lets a clerk actually double-spend it), and a control layer with real holes — 4 of 22 Permission flags are declared but never enforced anywhere (customer deactivation is a completely ungated write path today), QBO OAuth tokens store in plaintext unless an env var nobody has set is set, and a legacy /products/import-run route lets an admin push a full unstaged vendor feed straight into the live 31k-part catalog behind nothing but a typed phrase. Verification also REFUTED the scariest claim (Product Detail quoting a stale 30% price — the headline price is actually corrected client-side; only a minor competitor-card caption is stale, downgraded to low), so the core pricing story is better than the raw audits suggested. Nothing found corrupts the ledger itself; every confirmed high is a days-not-weeks fix. That is the definition of a B-: a strong engine wearing an unfinished safety harness.

## Phase-1 (live trial) readiness verdict

PARTIAL — honestly closer to yes than no, but not today. The full daily loop (quote -> SO -> PO -> receive -> invoice -> payment -> cores -> QBO push) genuinely works end to end with correct math, verified by passing full-chain tests, not by plan-doc claims. A counter person can run real parts operations on it and the ledger will be right. But three things WILL cause chaos within the first week of live use if not fixed first: (1) the quote header Disc% field silently does nothing while confirming 'Saved' — a clerk will verbally quote a discounted total that never appears on the printed invoice, and the first customer dispute will torch trust in the whole system; (2) cancelling an SO with a deposit and choosing 'credit' books the same dollars twice (customer credit_balance AND a still-applyable unapplied payment) — a real accounting error a bookkeeper will eventually find the hard way; (3) there is no double-click guard on Record Payment, the single most-repeated money action at a busy counter. Additionally, JAKS_FERNET_KEY must be set BEFORE the live QBO company is ever connected, or the standing QuickBooks refresh token lands in plaintext in every backup. All four are small, well-scoped fixes (roughly 1-2 days total). Land them, and this is ready for a supervised 30-day trial. Ship without them and the system's math will be right while its users stop believing it.

## Top risks (ranked, post-verification)

### 1. Quote header Disc% field is silently inert — saves, shows green 'Saved', total never changes
**Severity:** HIGH (verified CONFIRMED)

This is the counter hot path. QuoteService.update_header (quote_service.py:864-884) only setattr()s quote.discount_pct; no property in models/quote.py ever reads it — Quote.subtotal/total derive purely from per-line discounts. Autosave (quotes.py:1009-1046) returns a green checkmark, so the clerk gets active false confirmation. A verbally-quoted blanket discount will not match the printed/converted document. First customer dispute destroys trust in the whole ERP.

### 2. SO deposit 'convert to credit' on cancel double-books the liability
**Severity:** HIGH (verified CONFIRMED)

sales_order_service.py:846-869 bumps customer.credit_balance but never allocates against the original deposit Payment, so amount_unallocated stays fully open. Verification proved the blast radius is live: payments/detail.html still renders a working 'Apply Unapplied Balance' form for the stale deposit — a clerk can apply the phantom payment to a new invoice while the customer also spends the credit. Same dollars, paid out twice. The existing test only asserts credit_balance went up, so CI can't catch it.

### 3. QBO OAuth tokens stored in plaintext unless JAKS_FERNET_KEY is set — and it is not set
**Severity:** HIGH (verified CONFIRMED; becomes critical the day the live company is connected)

qbo_client.py:66-82 silently falls through to plaintext with a one-time backend log warning; /qbo/connect (qbo.py:35-42) never checks; the Settings UI has zero indication. A standing refresh token = full read/write on the real QuickBooks company, and the backup system faithfully copies that plaintext token to OneDrive/offsite. Verified independently against the live env (key unset). Must be a hard pre-go-live gate.

### 4. RBAC has unenforced flags and one completely ungated destructive route
**Severity:** HIGH (verified CONFIRMED — and worse than originally claimed)

15 of 22 Permission flags have zero deny-path tests, but verification found 4 of those (MERGE_CUSTOMERS, CHANGE_SETTINGS, DEACTIVATE_MASTER, SEND_SMS) have no assert_can call site anywhere — they are dead enum entries implying protection that does not exist. Concretely: POST customer_deactivate (customers.py:2079-2086) has no permission check of any kind. Any logged-in user can deactivate customer master records today, and any future refactor that drops an assert_can elsewhere ships silently.

### 5. Legacy /products/import-run writes a full vendor feed straight to the live catalog, bypassing the entire Smart Import review queue
**Severity:** HIGH (verified CONFIRMED)

products.py:1074-1117 calls full_import directly — no ImportCandidate staging, no row cap, no requirement that a dry run ever happened; the only gate is admin + typing 'APPLY TO LIVE CATALOG'. One bad column mapping = wrong titles/vendors/costs across the 31k-part catalog in a single POST. The whole point of Smart Import is defeated by a door left open next to it.

### 6. Owner's #1 data complaint ('imports separated things badly') has a merge tool but no discovery tool
**Severity:** HIGH (verified CONFIRMED)

category_service.py has solid gated merge_category/brand/manufacturer, but nothing anywhere computes name similarity — the owner must eyeball a flat list to find 'Fuel Filter' vs 'Fuel Filters' vs 'FUEL FILTERS'. With 13k+ parts imported across multiple passes, split categories/brands silently skew markup defaults, reorder rules, and search relevance indefinitely. Also: the one retroactive tool that exists (reclassify-all) has no UI button at all — it is unreachable curl-only.

### 7. No idempotency guard on Record Payment — a double-click books the same cash twice
**Severity:** MEDIUM

The payment form (invoices/workspace.html ~659) has no submit-disable and the route (invoices.py:1140-1192) has no dedupe window. This is the classic real-world counter failure mode at a shop processing many cash/check payments daily — overstates amount_paid, can flip PARTIAL to PAID off money received once.

### 8. RA approve/receive and nearly all of WarrantyService have zero permission gates
**Severity:** MEDIUM

Any authenticated user — including a SALES role deliberately denied RECEIVE_PO and FINALIZE_INVOICE — can approve a Return Authorization and push RETURN_TO_STOCK inventory back on the shelf (ra_service.py has no assert_can at all), or record vendor warranty decisions/credits (warranty_service.py:399-441 writes VendorCredit rows ungated). Inconsistent with the correctly-gated core/vendor-return paths sitting right next to them.

### 9. QBO 'Modified' invoice tab is an actionable-looking dead end; AST tax retry is blind
**Severity:** MEDIUM

Payments against a synced invoice flip it into the 'Modified' tab (invoices.py:275-277) but push_invoice unconditionally returns 'already synced' — there is no invoice update path, so the bookkeeper is shown a queue with no action. Separately, when Intuit's Automated Sales Tax rejects the tax override, the retry lets QBO compute its own tax with no read-back comparison (qbo_service.py:213-224) — JAKS and QBO tax liability can silently diverge.

### 10. Dashboard Monthly Revenue chart will not tie to the Sales reports for the same month
**Severity:** MEDIUM

dashboard.py:246-283 includes core-charge deposit lines, ignores invoice-level discounts, and buckets by created_at instead of the coalesce(locked_at, created_at) basis every report uses. The owner's natural cross-check (glance at chart, drill into Sales by Customer) produces two different numbers by construction — trust erosion in whichever one is 'wrong'.

### 11. SO workspace hides the tax-inclusive total from the person collecting a Pay-in-Full deposit
**Severity:** MEDIUM

The Totals card (sales_orders/workspace.html:325-346) prints only subtotal and literally says 'on invoice' for tax, but the fulfill gate (service.py:512-522) enforces collection of so.total. Clerk collects the only number visible, then hits a hard block at fulfillment with the customer standing there.

### 12. Products CSV export silently drops rows found by cross-ref/vendor-part/engine search
**Severity:** MEDIUM

product_export_csv (products.py:954-1010) uses its own weak SKU/title/description filter instead of the shared _product_search_filter the list view uses — 'export what I see' is false exactly when a counter person searched by OEM number, the most common diesel lookup.

### 13. Custom-mapped vendor feeds silently misattribute cost writes to PAI
**Severity:** MEDIUM

_vendor_code_from_sku only recognizes the JAKS-<CODE>- prefix and falls back to PAI (product_import_service.py:73-89); an R3-mapped feed (e.g. SAMPA) with bare part numbers can overwrite PAI's vendor_cost under a normal-looking history entry — wrong cost basis, wrong margin, wrong reorder vendor. Only bites when onboarding a new vendor via the mapping screen, so fix before the next new-vendor feed, not necessarily before day 1.

### 14. Line-item workspaces cramped (not unusable) below ~1280px
**Severity:** MEDIUM (verified PARTIAL — downgraded from high)

Verification corrected the math: the fixed 284px rail with no responsive breakpoint leaves ~420-444px for the 9-column line table at 1024px-with-sidebar (not the claimed 200-350px; sidebar is off-canvas below 1024px). Real friction with horizontal scrolling on the highest-value screens, but a one-line flex-col/md:flex-row fix in 3 files.

### 15. Product Detail competitor-card caption shows stale 30%-fallback price
**Severity:** LOW (verified PARTIAL — downgraded from high)

The scary version was refuted: the headline Pricing-card price is corrected client-side by Alpine using the real default_markup_pct. Only the small 'Our price $X · lowest competitor $Y' caption (detail.html:382) reads the raw hardcoded-30% property. Fix by passing PricingService.sell_price_for into the route context.

### Invoices (List/Workspace) + Finalize + Totals/Tax + Payments + Credit Memos — B

**Status:** The money path is unusually disciplined for a Phase-1 build -- one shared totals engine, atomic finalize/void claims, permission gates, and a real credit-memo ledger -- but a handful of real gaps remain: no server-side block on discounting a core-charge line, payment allocation is not truly oldest-first despite the UI's promise, and reverse_credit_memo has a fragile legacy-match fallback that can hard-fail a reversal.

**Diesel-industry fit:** The invoice/payment/credit-memo core is well-suited to a heavy-duty diesel parts counter's actual daily friction points: core charges are modeled as a genuinely separate, never-taxed, never-discounted liability bucket with their own CoreCharge ledger and a companion print slip (matches how PAI/Interstate-McBee style counters actually track core deposits owed back); the ESN/engine-make/model fields on the invoice header and the ability to auto-assign serial numbers at finalize (fail-safe, non-blocking) reflect real warranty-traceability needs in this trade; credit-hold as WARN-not-BLOCK matches how a small diesel shop actually operates (you don't turn away a longtime fleet account at the counter, you flag it and let the owner decide); and the CC-surcharge-at-payment-time-only design correctly avoids the common trap of baking a card fee into a quoted/printed total that then doesn't match what the customer is actually charged if they pay cash. The gaps found (no line audit trail, no payment dedupe guard, no service-side discount gate on core lines) are exactly the kind of things that bite a busy parts counter processing many walk-in cash/check/card transactions per day -- not exotic edge cases, but the ordinary failure modes of a real counter operation.

### QBO / QuickBooks Online Accounting Sync (app/routers/qbo.py, app/services/qbo_service.py, app/services/qbo_client.py + invoice/settings integration) — B-

**Status:** A genuinely careful one-way (JAKS→QBO) accounting-summary push with real fail-soft guarantees and good RBAC/idempotency — but token encryption is opt-in with zero UI visibility, and a "Modified" invoice-list filter tab is a dead end with no re-sync action behind it.

**Fully working:**

- OAuth connect/callback/disconnect: app/routers/qbo.py:35-69 + app/services/qbo_client.py:177-293 — real authorization-code flow over httpx, CSRF state persisted+verified (qbo_client.py:184-186, 220-222), tokens/refresh-token stored, disconnect revokes with Intuit best-effort then always clears locally (qbo_client.py:272-293). Covered by tests/test_qbo_sync.py:367-419.
- Token auto-refresh: QBOClient._ensure_token/_token_expired (qbo_client.py:312-325) refreshes ~90s before expiry; a stale 401 mid-flight triggers one retry (qbo_client.py:350-353). 429 rate-limit gets one bounded retry-after wait (qbo_client.py:354-363).
- Fail-soft contract is real, not just commented: every push method (push_invoice qbo_service.py:193-244, push_payment 362-466, push_vendor_bill 666-727, push_credit_memo 789-835) wraps the QBO call in try/except, calls mark_sync_failed/_mark_doc_failed on any exception, and returns a dict — never raises past the RBAC gate. Verified in tests/test_qbo_sync.py:299-326 and tests/test_qbo_push_batch.py:78-96 (push_invoice_is_failsoft_and_never_raises).
- Duplicate-sync prevention (sequential): push_invoice/push_payment/push_vendor_bill/push_credit_memo all check the stored qbo_*_id FIRST and short-circuit with skipped:'already synced' (qbo_service.py:200-201, 392-400, 684-685, 799-800) before any network call. Verified by test_already_synced_is_skipped (test_qbo_sync.py:275-282).
- RBAC on every push: Permission.REPUSH_QBO asserted before any lookup/network call (qbo_service.py:196,380,677,795); SALES role has no REPUSH_QBO (app/services/base.py:84-86), only BOOKKEEPING/ADMIN do (base.py:64-77). Route catches PermissionDeniedError and flashes, never 500s (qbo.py:96-99,123-126,159-160,184-187). Verified tests/test_qbo_safety_fixes.py:309-464.
- Audit trail: every push outcome (success AND failure) writes an AuditLog row via _audit_push (qbo_service.py:158-176), attributed to current_user_id, itself wrapped in try/except so an audit-write failure can never break the fail-soft contract.
- Invoice-push status/pushability gate: only OPEN/PARTIAL/PAID invoices are pushable (qbo_service.py:91,202-203) — a DRAFT invoice is refused before any QBO call. Verified test_draft_invoice_not_pushed (test_qbo_sync.py:351-365).
- Void-after-sync is hard-blocked: InvoiceService.void_invoice raises if invoice.qbo_invoice_id is set, forcing the credit-memo correction path instead of leaving QBO's AR open forever (app/services/invoice_service.py:1089-1101). This is the correct design and is unconditionally enforced (no bypass branch, per the §21 comment at line 1083-1094).
- Bulk push (/qbo/invoices/push-batch, qbo.py:259-284) offloads the blocking per-invoice loop to a worker thread via run_in_threadpool (qbo.py:227-256,272-278) so it never freezes the event loop; each invoice is pushed independently (one failure doesn't roll back others) — verified test_push_batch_failure_in_middle_does_not_abort_the_rest (tests/test_qbo_push_batch.py:98-124).
- Background retry worker (app/main.py:731-770) re-attempts ERROR-status invoices/payments/vendor bills/credit memos every ~30 min, each under a per-document retry ceiling (failed_invoice_ids etc., qbo_service.py:265-330), running as system actor (current_user_id=None) which passes the REPUSH_QBO gate by design.
- Cost/inventory/PO data is NOT pushed to QBO: the push maps every line to one of ~8 generic income items by line_type (DEFAULT_ITEM_MAP, qbo_service.py:57-71) with SKU riding along only in the line Description (qbo_service.py:1074-1076) — QBO never sees a parallel per-SKU item catalog, per-unit cost, or on-hand quantity. This matches the stated goal of clean bookkeeping-only sync.
- Card surcharge correctly excluded from the invoice/payment total and pushed as its own idempotent SalesReceipt (qbo_service.py:525-605), keyed by a deterministic DocNumber (JAKS-SC-{id}) and a persisted qbo_surcharge_receipt_id column checked before any query, closing the query-then-create double-book race (qbo_service.py:542-556). Verified test_repush_does_not_duplicate_surcharge_receipt (test_qbo_safety_fixes.py:608-624).

Functionally correct but means a renamed QBO account (even a harmless rename, e.g. 'Cost of Goods Sold' → 'COGS') silently breaks all bill pushes with an actionable error (good) but with no proactive detection until the next push attempt (the Settings→QBO Accounts page's verify dict, settings.py:864, only checks at page-load time, not continuously).

**Missing:**

A QBO-side edit or deletion is invisible to JAKS.
- No automated Sales Tax reconciliation: when the AST-rejection retry fires (qbo_service.py:213-224), the resulting QBO tax amount (computed by Intuit, potentially different from JAKS's tax_amount) is never read back and compared/logged — see the AST item under partially_working.

### Cross-cutting data integrity + security + money-path safety (auth, CSRF, permissions, demo-wipe gate, transaction atomicity, audit log, secrets, SQL-injection surface, inline migrations) — B+

**Status:** Genuinely hardened for a small-team LAN/internet-exposed deployment - real auth+CSRF+RBAC+atomic money paths - but QBO secrets default to plaintext-at-rest unless an env var is set, and RBAC is enforced only where a service author remembered to call assert_can.

**Fully working:**

- Login + session: PBKDF2-SHA256 (240k iterations), constant-time compare, itsdangerous-signed cookie, HttpOnly+SameSite=Lax, Secure-flag conditional on HTTPS/X-Forwarded-Proto (app/auth.py:45-115, app/routers/auth.py:143-155).
- Auth enforcement is a real gate: app/main.py:162-176 enforce_login middleware redirects every unauthenticated request except an explicit exempt set ({'/login','/logout','/health'} + /static/ + /api/leadfinder + /p/); the JAKS_SKIP_AUTH test bypass only fires when the active engine is literally in-memory (app/deps.py:22-34, checked again at app/main.py:165-167), so a stray env var can't disable auth against the real file DB.
- Default-password rotation gate: app/main.py:210-244 forces any signed-in user whose hash still verifies the shipped default ('admin'/'bookkeeper', app/main.py:193) to /account until rotated, including HTMX (HX-Redirect) - end-to-end with app/routers/auth.py:186-219 change_password (verifies current, min-length 8, confirms match, single db.commit()).
- Brute-force login lockout: 5 fails per username+IP -> 60s lock (app/routers/auth.py:52-102, applied at 113-136); same redirect for unknown-user vs wrong-password (no account enumeration); correctly test-bypassed only under the suite (_throttle_active -> app/security.py:_test_bypass, in-memory-engine gated).

- Core-charge double-credit guard is a real idempotency stamp, not a TOCTOU-vulnerable check: core.credit_issued_at is checked before mutation and the guard is explicitly documented as closing a double-issue bug (app/services/core_service.py:1112-1160).
- SQLite foreign-key enforcement is turned ON at the connection-pool level via an SQLAlchemy connect event (app/database.py:31-35) - without this every ForeignKey in the schema would be enforcement-free and deletes could silently orphan invoice/PO/core-charge rows.

**Partially working:**

**Built but weak:**

- The admin/bookkeeper default-password gate and the brute-force lockout are both in-process-only state: a lockout dict (app/routers/auth.py:54, comment at :49 explicitly flags 'single-box deployment; a restart clears it') and the password-rotation check re-query the DB per request but have no distributed/multi-worker concept - fine for the actual single-Windows-box deployment target, but would silently stop protecting anything the moment this app is ever run behind more than one worker process.
- CSP allows 'unsafe-inline' and 'unsafe-eval' in script-src (app/security.py:200-216) - a documented, deliberate tradeoff for Alpine.js inline expressions, but it meaningfully weakens the CSP's XSS mitigation value; any reflected-XSS bug elsewhere in the ~/products, /customers, /quotes template surface would not be blocked by this CSP the way a stricter nonce-based policy would block it.

**Missing:**

- No rate-limiting or account lockout on the /account/password change endpoint itself (only /login has throttling) - a signed-in session could be used to hammer current_password guesses if a session token were somehow obtained without the actual password (low practical risk given session tokens are themselves signed and hard to forge, but the asymmetry is real).
- No CSRF/session revocation on password change - app/routers/auth.py:186-219 change_password does not invalidate other active sessions for that user, so a stolen session cookie continues to work after the legitimate user rotates their password from a different device.
