## A. Executive Summary

**Is this worth continuing? Yes.** This is not a generic ERP with diesel labels glued on. The diesel-specific concepts are baked into the schema and the service layer: true multi-vendor sourcing (PAI/IMB/SAMPA per part), OEM + competitor + vendor-alt cross-references, engine fitment (make/model/CPL/ESN-range), a two-direction core lifecycle, ESN on warranty claims, a working 3-way match, and moving-average COGS written only on receipt. The quote → SO → PO → receive → invoice → payment → core spine runs end-to-end **today** with one authoritative totals engine, money asserted to the cent, and 2,421 real tests including true end-to-end chains. **Overall grade: B−.**

**Biggest problem:** A short cluster of *confirmed* defects sit directly on money, data-integrity, and confidentiality paths — and most are one-to-few-line fixes, which is exactly why they're inexcusable to leave in. The worst three: (1) **Reports and Dashboard have zero role authorization** — any logged-in clerk sees full cost basis, AR aging, and captured competitor pricing, on a LAN-exposed `0.0.0.0` server still seeded `admin/admin`; (2) **vendor name/code have no uniqueness constraint** — one duplicate "PAI" silently forks all cost history and breaks the 3-way match, and it gets worse the longer you wait; (3) **the FULL-payment gate checks subtotal, not subtotal+tax**, so a $10,000 taxable special order ships after collecting $10,000 against an invoice that reads $10,800.

**Biggest opportunity:** You are ~10 small fixes away from a system that genuinely runs the counter better than QuickBooks + Shopify + spreadsheets — specifically because of part-number search across normalized SKU/OEM/vendor surfaces, real cores, and a real quote workspace. Nobody sells you that combination off the shelf for a diesel parts shop.

**Best next step:** Add the role gate to `reports.py` + `dashboard.py`. It's the highest-severity confirmed defect, it's a few lines, and it's pure downside risk with no upside left undone. (Full reasoning in section H.)

## C. Broken / Risky Items (ranked by severity, all CONFIRMED)

1. **[HIGH] Reports + Dashboard have no authorization.** `reports.py:36` imports only `get_db`; no route carries an auth dependency and `ReportService` has zero `assert_can` checks. A SALES/READ_ONLY clerk can open inventory-valuation, AR-aging, and lost-sales (captured competitor prices). On `0.0.0.0:8000` this leaks your whole confidential pricing + AR picture to the lowest-trust user.
2. **[HIGH] Vendor name + vendor_code not unique.** `vendor.py:15` — no constraint, no duplicate probe in either create path (`vendors.py:197`, `:236`). A second "PAI" is one submit away; POs split across phantom vendors, cost history and 3-way match can't reconcile, QBO vendor resolution breaks, and `vendor_code` collisions alias the `JAKS-[CODE]-[part#]` SKU namespace. Gets harder to unwind every day.
3. **[HIGH] Vendor bills auto-approve on a clean match.** `po_service.py:867` sets APPROVED unconditionally when no discrepancy fires; `approve_bill` (`:1108`) then refuses anything already APPROVED — so a clean bill can *never* route through a human. Most PAI/IMB invoices match, so the majority auto-approve and queue for QBO with no AP touch. A cost error inside the $0.01 tolerance passes silently. One-line fix (default PENDING) + an Approve button.
4. **[HIGH] FULL-payment gate uses subtotal, not subtotal+tax.** `sales_order_service.py:458` gates on `so.subtotal`; SalesOrder has `is_taxable`/`tax_rate_snapshot` but no `.tax_amount`/`.total` property (Quote has them). A $10k taxable order fulfills+invoices after collecting $10k against a $10,800 invoice. You ship before fully collecting, on exactly the high-value orders where the gap is biggest.
5. **[HIGH] Cancelled SO lines print as live order lines.** `cancel_line` (`sales_order_service.py:279`) sets `qty_ordered=qty_invoiced` and never sets `qty_cancelled`; `print.html:326` only skips when `qty_cancelled>=qty_ordered` (never true) and has no `line_status` check. Every printed SO shows cancelled lines as live — wrong parts pulled, customer disputes. One-line template fix.
6. **[HIGH] QBO posts every invoice and payment on the sync date.** `qbo_service.py:806-819` and `:371-379` build payloads with no `TxnDate` (the vendor-bill payload at `:498` sets it — proving the field is known and was simply omitted on the AR side). Invoice in April, sync in May → books May revenue. P&L, AR aging, and sales-tax filings are wrong from the first push. **QBO is untrustworthy for accounting until this ships.**
7. **[HIGH] Garbage categories on direct import + same physical part imported twice.** `product_import_service.py:1717-1732` creates any level-1 category from the scraper's Type column with no allowlist and no `needs_review` flag — permanently polluting the classification tree. Separately, the full-import dedup key is `(vendor_code, vendor_sku)`, so the same physical part from PAI and IMB becomes two Products with two SKUs — splitting inventory, pricing, cores, and margin.
8. **[HIGH] Multi-PO single-shipment receiving unimplemented.** The receive route (`purchase_orders.py:914`) iterates one PO's lines; the post-loop status update (`po_service.py:489`) only updates the *last* PO. PAI routinely ships multiple POs on one truck — a daily scenario, not an edge case.
9. **[HIGH] Competitor part-number search is the one unindexed hot path.** `search_service.py:240` / `products.py:120` run a 10-function normalization with a leading wildcard against `CompetitorPrice.competitor_part_number` at query time — the only part-number surface absent from `search_index` `_TARGETS` with no `_norm` column. Once ATL/HHP data loads, every keystroke of an HHP number is a full-table scan that stalls the counter mid-sale.
10. **[HIGH] No dead-stock report for a 13k-SKU catalog.** No service method, route, or template. Dead stock is the #1 working-capital report for a distributor and the owner is blind to it.
11. **[HIGH] Engine picker disconnected from the Manufacturer table + no bulk re-classify.** Pickers pass `constants.ENGINE_MAKES`, never the owner-editable `Manufacturer` table; there's no `/reclassify-all`, so editing keywords does nothing for the ~13k already-imported parts; `ProductApplication` (CPL/ESN fitment) has no batch importer, so "what fits a Cummins ISX CPL 2732" returns nothing for un-annotated parts.
12. **[HIGH] QBO bulk push blocks the async event loop.** `qbo_push_batch` is `async` but calls synchronous `httpx` (45s timeout each) and `time.sleep` on retry, all on the loop. A Sync-All of 50–200 invoices freezes the entire app for minutes. Fix: make the route a plain `def` so FastAPI threadpools it.
13. **[MEDIUM] `available_credit` ignores `credit_balance`.** `customer_service.py:345` / `customer_metrics_service.py:113` compute `limit − open_ar` without adding core-return credits — understates available credit. Medium because it only *warns*, never blocks.
14. **[MEDIUM] Default admin/bookkeeper passwords printed in the launch .bat, no forced rotation, LAN-exposed.** `Start JAKS ERP.bat:12` echoes "Login: admin / admin"; `main.py:295/317` seed `admin/admin` and `bookkeeper/bookkeeper`; the warning banner is dismissable. Medium (LAN-only attacker) but must be force-rotated before real employees log in.
15. **[MEDIUM] ESN gate off by default.** `warranty_service.py:148` gates on `warranty_require_esn` defaulting to `false` with no seed row; PAI/IMB reject blank-ESN claims. Medium (not auto-credit — `credit_customer` is a separate manual button, so loss needs two human errors).

### What you do NOT need to fix (loud claims the verification pass REFUTED — don't waste a minute on these)
- **CSRF is fully implemented** as ASGI double-submit middleware (`security.py:92`, registered `main.py:98`), with tests. The old go-live note is stale.
- **The core-charge customer ≥ vendor guard exists** and is enforced at all three product write paths (`product_service.py:65-82`, call sites 117/198/358). No path can persist an inverted core charge.
- **NSF-DRAFT money loss is not real** — BOOKKEEPING already holds both REVERSE_PAYMENT and FINALIZE_INVOICE (`base.py:64-76`); the scenario can't occur. (The bare `except` is still worth tightening for hygiene.)
- **Alembic "silent swallow" is covered** — every 0002–0007 column is mirrored in the unconditional inline migration list (`database.py:320-349`). Residual risk is only future-developer discipline.
- **The `test_phase2_seams` xfail pins an already-fixed bug** — `quotes.py:407-408` reads the correct keys now. Drop the stale xfail; the counter sees the right outstanding-cores dollar value.
- **Inventory cache/ledger "drift" is NOT a live accounting bug** — SQLAlchemy's unit-of-work makes the claimed mid-transaction divergence impossible. It's a *code-duplication maintenance* risk (4 services repeat the pattern), not a money bug. Downgraded to LOW.

## D. Duplicate / Unnecessary Items

**Real duplication to consolidate:**
- **Engine make/model stored twice.** `Product.engine_manufacturer` is free-text *and* the `Manufacturer` table exists, with no FK between them. Two sources of truth that silently diverge. → Make the picker read the table; treat the table as canonical.
- **`brand`/`manufacturer` free-text on Product vs the `Brand`/`Manufacturer` tables.** The importer can write "PAI Industries" and "PAI" as two brands. → Constrain to the managed lists; add a brand-merge action (categories already have merge; brands don't).
- **Product search implemented twice** (the `/products/?q=` list route and `SearchService`) — must be kept in sync by hand. → Extract one shared query builder.
- **Inventory cache+ledger write pattern duplicated across 4 services.** Not a live bug (refuted), but a maintenance trap. → Extract one helper.
- **`compute_match_line` cost logic exists in multiple copies** (the 4th copy was never updated for the qty-ordered ceiling). → Single source.
- **`category_code` frozen at mint** can permanently differ from a product's actual category after re-categorization. Stale denormalized copy. → Decide: recompute, or hide it as derived-only.

**Overbuilt / unnecessary for this stage (leave dormant or postpone — do not invest now):**
- **ProductKit / BOM** tables exist with no router, service, or explosion logic. Dormant scaffold. Don't build the explosion engine until the spine is locked.
- **ESNLookup** is a Phase-3 stub. Fine as a stub; don't wire vendor portal APIs yet.
- **ProductSerialNumber** infra without a lookup UI — keep the capture, defer the screen.
- **MarkupTier** table + service with no admin UI — either ship a tiny CRUD or stop referencing it.
- **Messaging Send** (email/SMS) is log-only until SMTP/Twilio — leave it that way; don't build delivery now.
- **AI categorization service** — the model id at `ai_categorization_service.py:46` is unverified; confirm it even works before relying on it, and don't expand it.
- **eBay boundary** — postpone entirely.

## K. Final Brutal Opinion

This is a **smart investment, not a distraction** — but only if you treat the next two weeks as *finishing* work, not *feature* work. You have already built the hard, valuable, diesel-specific 80%: the search across normalized part-number surfaces, the two-direction core lifecycle, the 3-way match, and a single authoritative money engine with 2,421 tests behind it. That is real, and it's the part nobody hands you off the shelf.

What's holding it back is not architecture and not scope — it's a dozen small, confirmed defects sitting on the most important paths, plus a habit (visible in the git status and the memory index) of starting the next impressive thing before closing the last unglamorous one. The single most damaging pattern this audit found is that *the cheap fixes are the dangerous ones*: a one-line template check is letting cancelled lines print as live, a missing `.total` property is letting taxable orders ship under-collected, a missing `Depends(...)` is exposing your entire cost basis. Those don't survive a serious operator's first week.

**The verdict:** Stop adding subsystems. Clear the Phase-0 list (every item is Low difficulty), run JAK's on it daily for 60–90 days, and keep a hard rule — **no scraper/import data reaches the product master without passing through staging → review → approval** (you already built that pipeline; the only leak is the *direct* `full_import` path, which this audit flags). Do that, and you'll have something genuinely worth either running forever internally or, after Phase 6, selling. Keep chasing ProductKit explosion and ESN portal APIs before fixing the print template, and it becomes an expensive hobby. The work is good. Finish it.
